# Identity linking and first-sign-in matching

Status: Implemented. `CONTEXT.md` describes the implemented behavior. Verification: `make check`, 48 unit tests, and 29 end-to-end tests pass.

Implementation note: the supported Jellyfin 12 stack opens **Add User** as a page, rather than a modal. The optional expected identity entry extends that native creation form. New UI strings use the existing translation dictionaries with English fallback for entries not yet translated.

## Problem and outcome

Today a new Identity Provider identity can use an existing Jellyfin User only if its verified email equals that Jellyfin User's username. The plugin then saves an Identity Link keyed by issuer and `sub`. This is convenient for email-named Jellyfin Users but does not cover users whose Jellyfin usernames differ, or Identity Providers that supply a useful `preferred_username` but no verified email. Users cannot inspect or change their Identity Links, and administrators have no link-management UI in the Jellyfin User editor.

Provide three complementary paths: retain verified-email matching as the default, optionally match first sign-ins by `preferred_username`, and let an authenticated Jellyfin User explicitly link their own Identity Provider identity. Let users unlink themselves and let administrators manage a Jellyfin User's links and unlink opt-outs from a new OIDC tab in that user's dashboard editor, with an optional OIDC identity field in the New User modal. A returning identity must always resolve by its Identity Link, never by a newly selected matching rule.

## Terms and scope

- **Jellyfin User** owns permissions, credentials, and media activity.
- **Identity Provider** authenticates the identity; this feature continues to support one configured provider.
- **Identity Link** binds a configured issuer and `sub` to a Jellyfin User ID.
- **Email Match** remains a case-insensitive match between verified Identity Provider email and Jellyfin User username.
- **Preferred Username Match** is a case-insensitive match between a non-empty top-level `preferred_username` and Jellyfin User username. It is not proof that the identity owns a pre-existing Jellyfin User.
- **Unlink opt-out** records an issuer, `sub`, and former Jellyfin User ID after an explicit unlink. It prevents automatic matching or provisioning of that identity and automatic reassignment of that Jellyfin User while the opt-out stands.
- **Pending Admin Match** is an administrator-entered verified email or preferred username associated with one Jellyfin User for a future sign-in. Once used, it becomes an Identity Link and the pending value is consumed; it is not a permanent claim-based alias.
- **Open enrollment** means both group lists are empty: an authenticated Identity Provider identity can sign in without group claims, and its Jellyfin User is non-administrator.

This feature does not merge Jellyfin Users, transfer media activity, add a second Identity Provider, or introduce nested claims or manual OIDC endpoint overrides. It is designed for Jellyfin Web; other clients continue to use the normal OIDC sign-in behavior. Unlink does not terminate an existing Jellyfin session or revoke an Identity Provider session.

The feature also improves the Jellyfin Web sign-in button so users can recognize a supported Identity Provider by name and icon without changing authentication behavior.

## Requirements

### Identity resolution and claims

1. Add a provider-wide **First sign-in matching** setting with **Verified email** (default) and **Preferred username** choices. Existing installations default to verified email. The setting affects only identities without an Identity Link. Selecting preferred username is an administrator decision to trust the Identity Provider to keep those values unique and non-reassignable; in that mode, a first sign-in may attach to an existing Jellyfin User with the same username.
2. Every OIDC sign-in requires a validated non-empty `sub` from the configured issuer. When either User Group or Administrator Group is configured, require membership in an Allowed Group as today. When both are empty, use Open enrollment instead, including if the group claim is absent. A linked identity resolves by issuer and `sub` before any matching or provisioning. Do not use `preferred_username` as a durable identity key.
3. In verified-email mode, an unlinked identity needs a non-empty email and `email_verified=true` for an Email Match or Provisioning. In preferred-username mode, it needs a non-empty top-level `preferred_username`; an email is optional and an unverified email is never used to match. The plugin continues to request its existing standard scopes and uses a returned email only when verified.
4. An already linked identity needs neither email nor `preferred_username` to sign in, regardless of matching mode. If a verified email is absent, skip email-derived username synchronization. This intentionally relaxes today's email requirement for linked identities, including manually linked identities.
5. For an unlinked identity, find exactly one Jellyfin User whose username equals the selected key, ignoring case. Deny ambiguous matches. If there is no match, provision a Jellyfin User with that key as username and an undisclosed random local password. Deny a create/rename collision rather than choosing a different Jellyfin User or silently appending a suffix.
6. Before matching or provisioning, reject an identity with an unlink opt-out. Do not let an unlinked `sub` automatically claim a Jellyfin User already linked to a different `sub` for this issuer or reserved by an unlink opt-out; require an explicit administrator resolution. Reject duplicate or conflicting issuer/`sub` records. An unlinked identity cannot take over an already owned Jellyfin User merely because its claim now equals that user's username.
7. Existing email-matched links retain today's verified-email-change rename behavior, including denial if the new name belongs to another Jellyfin User. Manually linked and preferred-username-matched links preserve their Jellyfin User username across claim changes. Store link origin or equivalent durable policy so changing the matching setting does not retroactively alter username behavior; treat legacy links as email-matched.
8. When a linked Jellyfin User has been deleted, remove the stale Identity Link as today and retry the selected first-sign-in rule, unless that identity has an explicit unlink opt-out. Deleting a Jellyfin User is not itself an unlink opt-out.

### Group access and Open enrollment

1. Empty User Group and Administrator Group lists mean Open enrollment. Do not require a group claim in this configuration. An unlinked eligible identity can Email Match, Preferred Username Match, use a Pending Admin Match, or be provisioned under the normal identity-resolution rules. Linked identities may also sign in. The selected first-sign-in claim is still required for automatic matching or provisioning; Open enrollment never removes the `sub` requirement or overrides an unlink opt-out.
2. Every sign-in in Open enrollment sets the Jellyfin User's administrator status to false, including for a previously linked administrator. Provision with Jellyfin's ordinary non-administrator policy. Group claims, if present, do not grant administrator access when no Administrator Group is configured.
3. If either group list is non-empty, preserve existing group admission: require a matching configured User Group or Administrator Group. A missing, malformed, empty, or unmatched group claim is denied, including for linked identities and dedicated self-service linking. A match in Administrator Group grants administrator rights; removing it removes administrator rights on the next eligible OIDC sign-in.
4. Change configuration validation so both group lists may be empty when OIDC is enabled. Preserve the existing rule that `DisableForAllUsers` requires an Administrator Group; Open enrollment cannot satisfy that requirement and cannot be combined with that password mode. Explain in the configuration page that leaving both group lists empty allows anyone authenticated by the configured Identity Provider to obtain a non-administrator Jellyfin User, including through a public provider such as Google.

### Self-service linking and unlinking

1. Add a provider-wide **Allow self-service Identity Links** setting on the plugin configuration page, default on for new and existing installations. Show an Identity Provider card in the signed-in Jellyfin User's profile/settings UI with its locally served selected logo and provider name, or the key icon and **SSO** for **Other**. When linked, show **Linked to {Provider name}**, the last verified email and/or preferred username returned by that identity when available, and **Unlink** when permitted. When unlinked, show **Not linked** and **Link Identity Provider** when permitted. Label missing claims as unavailable rather than inventing them; do not show a raw `sub`, client secrets, or tokens. Show status for the authenticated Jellyfin User only. When self-service is disabled, show read-only status but omit link/unlink actions and reject self-service start, completion, and unlink requests server-side, including in-flight linking attempts. Administrator actions and ordinary OIDC sign-in remain available.
2. A Jellyfin-authenticated request starts a dedicated OIDC challenge. Preserve a short-lived, single-use, server-side intent bound to the authenticated Jellyfin User ID, the initiating Jellyfin session, the configured issuer, and the link operation. The OIDC callback validates the OIDC response and intent, then returns an opaque one-time completion ticket to the profile page; it must not call normal match/provision/session-handoff logic. Jellyfin Web keeps its session token in browser storage, so the navigation callback must not assume it can authenticate that session from the request alone.
3. The profile page sends the completion ticket to a Jellyfin-authenticated endpoint. Recheck the same session and Jellyfin User, `sub`, and configured group admission rule before creating the Identity Link. Do not require email or `preferred_username` for explicit linking. Refuse to reassign a `sub` linked to another Jellyfin User or to add a second link to the same Jellyfin User in this one-provider design. An explicit link for the opted-out `sub` clears its opt-out atomically.
4. An existing link to the same Jellyfin User is idempotent. On a failed, expired, mismatched, or cancelled attempt, create no link and return to the profile UI with a safe error. Do not sign the browser in as another Jellyfin User as a side effect. Preserve the user's current session on success.
5. Unlink requires the currently authenticated Jellyfin User and removes only that user's Identity Link. Record an unlink opt-out for its issuer and `sub` in the same operation. Do not permit a caller to supply an arbitrary target user ID for self-service unlinking. An absent link is an idempotent outcome, not a request to unlink someone else. Reject self-service unlink when `DisableForAllUsers` is selected, even if a browser bypasses the disabled control.
6. Confirm permitted unlinks in a modal with clear text that OIDC will stop opening this Jellyfin User until they explicitly link again or an administrator restores access. In `DisableForLinkedUsersOnly`, reapply the password policy immediately and explain that the user still needs a known local password to use it. In `DisableForAllUsers`, show why self-service unlink is disabled. Do not promise recovery of a random provisioned password.

### Administrator management

1. Inject an **OIDC** tab into Jellyfin Web's **Dashboard > Users > Edit User** page. It is scoped to the currently edited Jellyfin User, not a server-wide list. Use the same Identity Provider card layout as the personal profile: selected local logo or key icon, provider name, link status, last verified email, and preferred username when known. Keep the relevant **Link by signing in** or **Unlink** button in this card alongside the identity summary. Administrator-only identity details such as linked issuer and subject or link origin may appear below that summary inside the card. Put Pending Admin Matches, expected email/username entry, and other administrator settings outside the card in their own section. Handle a deleted Jellyfin User or a changed editing target without showing stale identity data. The plugin configuration page continues to hold provider-wide settings only.
2. Provide a separate, explicit **Unlink** action for the edited Jellyfin User, with no replacement email or username required. It removes the current Identity Link, creates the same opt-out as self-service unlink, and rechecks local-password policy. Provide confirmation and an explanation of the next sign-in behavior. Administrator unlink remains available even when self-service unlink is disabled by the password mode, with a clear lockout warning. Editing, adding, cancelling, or correcting an expected email/username must never implicitly unlink a user.
3. Show the expected verified email / preferred username controls only when the edited Jellyfin User is **unlinked**. While linked, show the existing identity and last-seen claims read-only with an explicit **Unlink** action; do not show a replacement matching field or silently replace the link. After the administrator unlinks, allow them to enter or change either an expected verified email or expected preferred username for that Jellyfin User's next OIDC sign-in, regardless of the global matching setting. Validate the selected claim on that sign-in (`email_verified=true` for email); if it matches, create an issuer + `sub` Identity Link to the selected Jellyfin User and consume the Pending Admin Match. That resulting link is durable; the claim value must not remain a standing alias that another `sub` can use later. If the identity was explicitly unlinked from this Jellyfin User, only a successful admin-directed match, confirmed administrator link-by-sign-in, or explicit self-service relink lifts its opt-out. Never grant access by clearing an opt-out alone.
4. Reject duplicate Pending Admin Matches, ambiguous claim values, targets already linked to another `sub`, and matches inconsistent with an opt-out reserved for another Jellyfin User. A pending value reserves its target Jellyfin User against other automatic matches until it is used or cancelled. Provide an administrator action to cancel an unused Pending Admin Match. Show the edited Jellyfin User and claim/value in confirmation; explain the trust requirement for preferred usernames.
5. Reject unauthorized reads and writes server-side, not only by hiding the tab. Validate that the Jellyfin User ID in admin requests is the one being intentionally edited; a browser route, DOM value, or cached UI selection is not authorization. Expose only the fields needed by each UI, never the full plugin configuration through a new user-profile API. Treat issuer and subject as sensitive identity metadata in the user-facing page and logs.
6. Link operations must use server-side, atomic or serialized updates against current link state. A stale browser configuration save must not erase a recently created link, opt-out, or Pending Admin Match, and simultaneous sign-ins and management operations must not assign the same identity to two Jellyfin Users. The tab refreshes after changes and displays a conflict rather than overwriting another administrator's action.
7. Add the same optional expected verified email / preferred username entry to Jellyfin Web's **Dashboard > Users > New User** modal. A blank value leaves Jellyfin's ordinary new-user flow alone. A supplied value creates a Pending Admin Match for the newly created Jellyfin User; it must never modify the global matching setting or create an Identity Link without a validated OIDC sign-in. If Jellyfin User creation succeeds but saving the Pending Admin Match fails, report the partial result and take the administrator to that Jellyfin User's OIDC tab to retry; do not claim that both operations succeeded or delete the newly created Jellyfin User.
8. On an unlinked Jellyfin User's OIDC tab, also offer **Link by signing in**. The administrator authenticates at the Identity Provider as the identity intended for that Jellyfin User; the plugin never asks for or handles the Identity Provider password. Start a dedicated OIDC flow bound to the authenticated Jellyfin administrator session and selected Jellyfin User ID. After callback, show the returned Identity Provider identity to the administrator and require explicit confirmation before committing issuer + `sub` to that Jellyfin User and clearing an opt-out for the same identity and former Jellyfin User. If the Identity Provider silently reuses a different identity's session, the administrator can cancel. Reject a `sub` linked elsewhere or a target that became linked while the flow ran. Keep the administrator signed in as themselves in Jellyfin throughout; do not run normal matching, provisioning, or session handoff. Once linked, hide both this action and expected-claim entry until an explicit Unlink.

## Behavior matrix

| Situation | Outcome |
| --- | --- |
| Existing Identity Link, Allowed Group | Sign in to its Jellyfin User by issuer + `sub`, regardless of match setting or missing email/username claim. |
| Both group lists empty, valid `sub` | Open enrollment: sign in by existing link or selected first-sign-in rule, with non-administrator status even when no group claim is returned. |
| No link, verified-email setting, verified email matches one unlinked Jellyfin User | Link and sign in to that Jellyfin User. |
| No link, preferred-username setting, claim matches one unlinked Jellyfin User | Link and sign in to that Jellyfin User; do not require verified email. |
| No link, selected key exists but Jellyfin User is linked to another identity | Deny; administrator must resolve the conflict. |
| Pending Admin Match, eligible identity proves its configured claim | Link to the selected Jellyfin User by issuer + `sub`, consume the pending value, and clear a matching opt-out. Future sign-ins use only the Identity Link. |
| No link, selected key does not match | Provision and link using the selected key. |
| No link, missing selected key, or ambiguous matches | Deny without provisioning. |
| Explicitly unlinked issuer + `sub` | Deny automatic sign-in, matching, and provisioning; explicit self-service relinking, confirmed administrator link-by-sign-in, or a successful Pending Admin Match to the former Jellyfin User is required. |
| At least one group configured, group missing or no Allowed Group matches | Deny, including during the explicit link flow; do not remove an existing link or background-terminate sessions. |

## Security and failure handling

- All self-service mutations require a validated Jellyfin session and target only its Jellyfin User ID. Admin mutations require Jellyfin administrator authorization. Do not trust a user ID, link ID, issuer, or `sub` supplied by browser code without checking current server state.
- The OIDC link challenge must bind the signed-in Jellyfin session to expiring, single-use, unpredictable server-side state. Validate the OIDC response at callback, but recheck the initiating Jellyfin session on the authenticated completion request before committing the link. The completion ticket must contain no identity data, be single-use and short-lived, and not permit use by another session. No successful callback may silently switch the browser to a different Jellyfin User.
- An attacker-controlled or recycled `preferred_username` can claim an unlinked pre-existing Jellyfin User. Document this trust assumption at the dropdown, default to verified email, and enforce uniqueness and conflict checks. Administrators should use explicit linking if the Identity Provider cannot guarantee stable, unique preferred usernames.
- Open enrollment deliberately grants ordinary Jellyfin access to anyone who can authenticate with the configured Identity Provider and supplies the selected matching claim. For a public provider such as Google, that can mean anyone with a Google identity. Never interpret a missing group claim as permission to sign in while either group list is configured. Keep the ban on disabling local passwords for all Jellyfin Users without an Administrator Group.
- On an opt-out, deny automatic provisioning as well as matching to avoid a second Jellyfin User with the same identity. Reserve the former Jellyfin User ID until an explicit relink or successful Pending Admin Match; a different `sub` matching its username must not bypass ownership checks.
- Changes to links or opt-outs do not retroactively revoke Jellyfin sessions; access/group rights are reevaluated at subsequent OIDC sign-ins. Do not log tokens, complete ID tokens, client secrets, or full claim payloads, and do not expose configuration secrets in new APIs.
- Return clear admin/profile conflict messages for stale or duplicate operations, but keep public sign-in errors non-enumerating. Failed persistence must not report success or leave contradictory link and opt-out state.
